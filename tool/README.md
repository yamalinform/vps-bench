# Устройство движка

Это внутренняя часть инструмента: она живёт **внутри образа** и запускается оболочкой
`run.sh`. Пользователю сюда заглядывать не нужно — ему адресован README в корне.
Здесь описано, как движок устроен и почему именно так, чтобы правку можно было внести,
не разбирая всё заново.

---

## Что вызывается

```
bash /opt/vpsbench/tool/vpsbench.sh --vantage ИМЯ [опции]
```

`--help` печатает полный список флагов. Самые нужные:

| Флаг | Смысл |
|---|---|
| `--impact observe` | **по умолчанию.** Щадящий режим: пробы короче и слабее |
| `--impact bench` | полная нагрузка; печатает предупреждение о её характере |
| `--depth quick` | **по умолчанию.** 3 повтора на метрику |
| `--depth full` | приёмка площадки: 5 повторов, длиннее пробы |
| `--only`, `--skip` | выбрать или исключить модули |
| `--no-deps` | ничего не устанавливать; недостающее помечается НЕДОСТУПНО |
| `--host-root DIR` | где искать опознание **хоста**, когда движок работает в контейнере |
| `--meta К=З` | записать пару в отчёт (через неё оболочка передаёт то, чего движок не знает) |
| `--dry-run` | показать план, оценку времени и что будет установлено; ничего не делать |
| `--selftest` | прогнать парсеры по фикстурам; ничего не меняет |

## Состав

```
tool/
├── vpsbench.sh        единственный вход
├── targets.conf       цели сетевых замеров; в результат идёт только МЕТКА, не адрес
├── lib/
│   ├── common.sh      маскирование адресов, факты, манифест, привилегии, os_check
│   ├── parsers.sh     разбор вывода инструментов — ТОЛЬКО по якорям
│   ├── measure.sh     повторы, медиана, разброс, снимки условий прогона
│   ├── deps.sh        базовый срез машины, решение «нужна ли установка», установка
│   └── selftest.sh    проверка парсеров по фикстурам, включая отрицательные тесты
├── modules/           00-precheck 10-host 20-cpu-crypto 30-cpu-general
│                      40-memory 50-storage 60-network 70-public
├── agent/             agent-up.sh, agent-down.sh — приёмная сторона сетевого замера
└── fixtures/          реальные выводы инструментов для самопроверки
```

## Три правила, на которых всё держится

**1. Значение берётся по якорю.** Имя секции, метка, структурный разделитель — но
никогда «последнее совпадение» и никогда номер поля без проверки. Основание не
теоретическое: четыре парсера подряд возвращали не пропуск, а **неверное число** —
задержку 14 мкс вместо 18 мс, скорость приёма вместо отдачи, чужой метод замера памяти.
Все четыре выглядели правдоподобно.

**2. У каждого парсера есть контрольный прогон с заведомо ненулевым значением.**
Ноль от «устройство не отвечает» неотличим от нуля от «взято не то поле». Проверка
живёт в `--selftest` и гоняется против сохранённых фикстур, а эталоны выведены
независимо — разбором тех же файлов по структуре, а не этими же парсерами.
**Отрицательные тесты обязательны:** тест, который не может провалиться, ничего
не доказывает.

**3. Отчёт строится по каноническому реестру** (`registry.py`), а не по тому, что
нашлось в данных. Поэтому его структура одинакова на любой машине, а неснятая метрика
остаётся строкой «не измерено» и не исчезает.

## Что стоит знать, прежде чем править

- **Все сравнения списков — под `LC_ALL=C`.** Сортировка в локали пользователя
  игнорирует пунктуацию, и `comm` на таких входах молча выдаёт ложные расхождения.
- **Код возврата важнее размера вывода.** Непустой файл ещё не значит данные:
  `dmidecode` без прав печатает баннер и падает.
- **`apt-get autoremove` не вызывается никогда.** Однажды он снёс полсотни посторонних
  пакетов, включая механизм обновлений безопасности. Мы знаем, что поставили, —
  удаляем ровно это, по манифесту.
- **Файлы `.sh` — только с переводом строки LF.** CRLF ломает даже строку интерпретатора.

## Сеть: нужна вторая сторона

Пропускная способность и задержка меряются между двумя машинами. На второй поднимается
приёмная часть — **на время замера, не как служба**:

```
agent/agent-up.sh     затем   agent/agent-down.sh
```

⚠️ Пакет `irtt` в Debian приходит с **включённой** службой, которая слушает UDP/2112
постоянно и переживает перезагрузку. Если движок ставит пакеты на хост, он такие службы
гасит и записывает это в манифест. В контейнере systemd нет, и проблема не возникает.

Чтобы померить канал в обе стороны, машины меняются ролями — **последовательно**:
та, что работает приёмной стороной, не должна одновременно гонять свою батарею.

## Публичные точки (модуль `70-public`)

Отдельный замер до Cloudflare и зеркал, для случая «второй машины нет». Он **не заменяет**
замер до своей машины и идёт отдельными метриками. Список точек, объём переноса (50 МБ)
и число потоков (1 и 8) зашиты в код: это часть методики, и их смена делает прогоны
несравнимыми ровно так же, как смена версии измерителя.
